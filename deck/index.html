Stage 1 · Workload specification

Work backwards from the workload, not forwards from the model

The failure pattern

Someone picks a model, then goes looking for a workload to justify it.

Every bad model decision I have seen started exactly this way.

A workload specification is the set of facts about demand and constraint that every later decision is allowed to depend on.

Nine numbers and six flags. If you cannot fill it in, you are not ready to choose a model — you are ready to go and ask someone a question.

Stage 1 · Derived demand

Two numbers decide more than the other thirteen

Burst ratio — 5.8×

0.23average requests / sec
1.33peak requests / sec

You never size for the average. Anything that cannot absorb a 5.8× burst either queues — blowing the latency budget — or drops requests.

Peak output tokens/sec — 467

2,067total tokens/sec (in + out)
467output tokens/sec

Input tokens are consumed in one parallel prefill pass. Output tokens are generated serially — and that is what occupies a GPU.

Size a fleet on total tokens instead of output tokens and you overshoot by 4.4×. That is a rack of GPUs bought for an arithmetic error.
Note · This is the most practically useful slide in Block 1. Most capacity plans in the wild get this wrong. 31M daily tokens total.

Stage 2 · Model class

First, kill the false binary

"Proprietary vs open-weight" is the question everyone asks, and it is under-specified. Open weights do not imply self-hosting. Proprietary does not imply a public endpoint.

ClassWeights held byInference run byPosture
Proprietary APIvendorvendorfastest to adopt; least control

Four real classes, not two. The highlighted row — proprietary in-tenant (Bedrock / Vertex / Azure Foundry) — gets you most of the data-residency and network-isolation story without owning a GPU fleet. It is the option most often skipped.

Stage 2 · Corrections

Three things people routinely get wrong

1 · "Open weight" is not "open source."
Most ship under bespoke community licences with acceptable-use terms and, in some cases, user-count thresholds. Licence review is a real gate with a real owner — not a formality you discover during procurement.
2 · Self-hosting is not a cost saving by default.
It substitutes a fixed cost for a variable one. It wins above a break-even volume and loses badly below it. We compute that point in Stage 5 rather than assuming it — and the answer will surprise you.
3 · Control is not binary.
The choice is not "vendor sees everything" or "we run the GPUs". Residency, retention, network path and audit are separable properties you can negotiate independently.
Note · Ask: has anyone here actually read a community licence end to end? The user-count thresholds catch people out at exactly the scale where it hurts.

Stage 2 · The method

Derive the weights. Do not invent them.

The hidden flaw in every scorecard exercise

Someone types in the criteria weights.

Whoever controls those numbers controls the outcome — and the reasoning becomes unfalsifiable.

So we do not type them. derive_weights() is a pure function of the WorkloadSpec.

def derive_weights(w): s = dict.fromkeys(CRITERIA, 0.30) # cost of being wrong → capability s["Answer quality"] += {...}[w.factuality] # budget left after fixed overhead head = w.p95_latency_ms - 600 s["Latency headroom"] += clip(7000/head, 0, 3) # volume, on a log scale s["Unit economics"] += clip(log10(w.daily_tokens)-6, 0, 3) # SHARE-weighted, not max-weighted si = (w.sensitivity_index - 1) / 3.0 s["Privacy / control"] += 0.15 + si*3.0 # capability gates s["Tool calling"] += 1.7 if w.needs_tools else 0 s["Multimodal"] += 1.9 if w.needs_vision else 0 ...
Tight latency budget raises the latency weight. Sensitive data raises the privacy weight. High volume raises the cost weight. Change Stage 1, and Stage 2 moves on its own.
Note · Show the notebook cell here if you can. The point is falsifiability: anyone can disagree with a coefficient, and that disagreement is testable. A typed weight is not.

Stage 2 · Fragility

Before you act on a scorecard, try to break it

Proprietary in-tenant 8.128 ← winner Proprietary API 7.990 Open-weight managed 7.743 Open-weight self-host 7.617 margin over runner-up 0.138

Perturb each criterion weight by ±40%, renormalise, and see whether the winner survives.

One criterion can flip it.
Privacy / control at −40% → Proprietary API wins, margin 0.004.

What that tells you to do

A weighted score that wins by 0.01 points is not a decision — it is a coin flip with extra steps.

The sensitivity analysis tells you exactly where to spend your evidence budget. For the fragile criterion, go and get a real artefact:

  • a benchmark run on your golden set
  • a data-processing agreement clause
  • a procurement quote
  • a security review sign-off
Name the artefact, not the opinion.

Stage 3 · Method

Compare capability profiles, not leaderboard positions

Benchmark tables go stale in weeks and rarely predict performance on your data, with your prompts, against your retrieval.

What does not go stale in weeks is the structural profile of a family:

  • Are the weights downloadable — and under what licence?
  • Which deployment surfaces can you reach it on?
  • Does it span small / medium / large, so you can route by difficulty?
  • Native tool calling? Native vision?
  • What is its relative cost position?
Structure decides viability.
Quality decides the pick.

Those properties tell you whether a family is architecturally viable at all.

Quality then chooses between the viable ones — and you measure that yourself, on your golden set, in Stage 7.
⚠ Verify before you quote.
Model names, context limits, modality support and prices all move. Check the provider documentation in the session agenda — OpenAI, Anthropic, Google Gemini, Meta Llama, Hugging Face, Azure OpenAI — before any of this reaches a real design document.

Stage 5 · Capacity

Availability sized this fleet. Throughput never got a vote.

SELF-HOSTED PRIVATE PATH (3.1% of traffic) ──────────────────────────────────────────── Peak output tokens/sec on this path 14.5 Sustainable tokens/sec per replica 1040.0 Replicas (HA floor applies) 2 GPUs 4 GPU cost / day $307.20 Platform staffing / day $271.23 TOTAL / day $578.43 Cost per Restricted request $0.9330

The Restricted path needs 14.5 output tokens/sec at peak. One replica could serve it seventy times over.

We run two anyway — because one replica is not a system, it is an outage waiting for a maintenance window.

So the private path costs roughly the same whether it serves 3% of traffic or 30%.

Its cost is driven by availability, not throughput. This is the most common surprise in self-hosting business cases, and it is why "we'll just self-host the sensitive bit" is rarely cheap.

Compare: $0.93 per Restricted request against a blended $0.0324 across the whole system. 29× more expensive.

Note · This slide alone is worth the block. The HA floor is the thing people forget when they scope 'a small private deployment'.

Stage 6 · The lesson

The vulnerability is architectural, and it fits on one line

Trust was assigned by the orchestrator, in one line, when it marked retrieved content trusted=True.

Everything downstream followed correctly from that.

The model read the policy and ignored it, because the injected note arrived with exactly the same authority as the policy did.

This is why "we'll put it in the system prompt" is not a control. The system prompt and the attacker's text end up in the same context window, and the model has no reliable way to rank them.

On LLM-as-judge
It scales, and it is genuinely useful for graded qualities — tone, completeness, style. It is also correlated with the thing it is judging: it shares training data, blind spots and sycophancy with the system under test, and it will happily rate a confidently wrong answer highly.
The rule
Use the judge for soft dimensions. Use deterministic assertions for anything you would be embarrassed to get wrong.

Note that every safety metric above is deterministic. That is deliberate.

Stage 8 · The principle

The model proposes.
Trusted software decides.

A model is a probabilistic component.
Authorization is a deterministic problem.

Every time you let the first thing answer the second kind of question, you have built a system whose security properties depend on a sampling temperature.
So divide the work.
Keep language and reasoning in the model.

Keep authorization, business rules, transactions and state in ordinary software you can test, review, and reason about.

Capstone · What the exercise tests

Not whether you can build a pipeline.
Whether your decisions are load-bearing.

In a notebook where the numbers are typed in, setting sovereign_only=True changes nothing — because nothing downstream reads it.

You would get a tidy diagram and a decision that quietly means whatever you want it to mean.
Here, one boolean eliminated three of four model classes, flipped the chosen class, replaced the reasoning model, dissolved the private route, changed the bill, and widened the latency failure from one route to all three.

Consequences propagate.

That property is the difference between an architecture and a diagram.

A useful test for your own designs:

Pick the requirement you are least sure about. Change it. If nothing else in your design has to move, either the requirement does not matter — or your design is not actually derived from it.

Both answers are worth knowing.

(Stage 1) Drivers Tool calling 16%, multimodal 13%, answer quality 13% — derived from the workload, not assigned. (Stage 2) Alternatives Proprietary API rejected: cannot carry Restricted traffic Open-weight managed rejected: lower capability, no clear gain Self-host everything rejected: cheapest, but fails p95 on every route and scores lower on capability Evidence Weighted score 8.128 vs 7.990. Sensitivity: flips only if the privacy weight drops 40%. (Stage 2) Recall@k 1.00, groundedness 0.90, attack success 0%. (Stages 7–8) Trade-offs $69/day above the cheapest compliant option. The Restricted tail costs $578/day — 8.3× the cost of serving everything else — and buys permission, not capability. (Stage 5) Open risks PRIVATE route misses p95 by 735 ms on 3% of traffic. BLOCKING — requires a separate SLO with sign-off, faster accelerators, or a reduced output-token budget on that route. (Stages 5, 9) Rollback Canary 5/25/50/100%. Auto-rollback on quality <0.80, any attack success, or p95 >5,000ms. Manifest fingerprint pins every version. Review On any model version change, retriever re-index, tool schema change, or data reclassification. (the capstone showed why)
